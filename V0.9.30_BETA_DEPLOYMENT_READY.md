## 🎯 What Was Implemented

### Problem Solved
Server Alpha (161.35.219.10) and Server Beta (185.182.185.227) were both mining independently, creating blockchain forks. When Server Alpha's blocks arrived at Server Beta via gossipsub, they were being rejected because Server Beta already had blocks at those heights. Result: Mining rewards from Server Alpha never synced to Server Beta.

### Solution: Fork-Choice Rule
Implemented a **heaviest chain wins** fork resolution algorithm based on cumulative difficulty (`total_difficulty` field in BlockHeader).

**Algorithm**:
1. When a block arrives via gossipsub, check if a block already exists at that height
2. If yes, compare cumulative difficulty:
   - Incoming block has **higher difficulty** → Accept (heavier chain wins)
   - Incoming block has **lower difficulty** → Reject (keep existing)
   - **Equal difficulty** → Use proposer ID as deterministic tiebreaker (lower ID wins)
3. Replace lighter fork with heavier fork in block storage

// v0.9.30-beta: FORK-CHOICE RULE - Heaviest chain wins
match storage.get_qblock_by_height(block_height).await {
    Ok(Some(existing_block)) => {
        let existing_difficulty = existing_block.header.total_difficulty;
        let incoming_difficulty = block.header.total_difficulty;

        if incoming_difficulty > existing_difficulty {
            // Heavier chain wins - fall through to processing
            warn!("🔀 [FORK RESOLUTION] Incoming block has higher difficulty");
        } else if incoming_difficulty == existing_difficulty {
            // Tiebreaker on proposer ID
            if block.header.proposer < existing_block.header.proposer {
                warn!("🔀 [FORK RESOLUTION] Tie - lower proposer ID wins");
            } else {
                return; // Keep existing block
            }
        } else {
            // Reject lighter fork
            return;
        }
    }
    Ok(None) => {
        // No conflict - proceed normally
    }
}

## ⚠️ Known Limitation: Balance Reorganization Not Implemented

**Current behavior**:
- ✅ Block storage correctly replaces lighter fork with heavier fork
- ❌ Balances from old fork are NOT rolled back
- ❌ Rewards from new fork are NOT applied

**Impact**: When a fork occurs, the blockchain state is correct but wallet balances may be incorrect until manually verified.

**Example scenario**:
```
1. Server Beta mines block 100 → Miner B gets 0.001 QNK
2. Server Alpha mines block 100 (heavier) → Should give Miner A 0.001 QNK
3. After fork resolution:
   - Block 100 replaced with Server Alpha's version ✅
   - Miner B keeps 0.001 QNK ❌ (should be removed)
   - Miner A doesn't get 0.001 QNK ❌ (should be added)
```

**Workaround**: Monitor fork resolution warnings in logs and manually verify balances.

**Future work**: Full balance reorganization will be implemented in v0.9.31-beta.

## 📊 Expected Behavior

### Normal Operation (No Forks)
- Blocks arrive via gossipsub
- No existing block at height → Accept immediately
- Process mining rewards → Update balances
- Height advances normally

### Fork Detected (Server Alpha heavier)
- Server Alpha's block arrives
- Server Beta already has block at that height
- Compare cumulative difficulty
- Server Alpha's difficulty is higher → **Accept**
- **WARNING logged** about balance reorg limitation
- Block replaced in storage
- ⚠️ Manual balance verification required

### Fork Detected (Server Beta heavier)
- Server Alpha's block arrives
- Server Beta's block has higher difficulty → **Reject**
- Keep existing block
- Log rejection
- Continue normally

## 🔍 Monitoring and Alerts

### Log Messages to Watch For

**Fork detected (heavier incoming)**:
```
🔀 [FORK RESOLUTION] Incoming block <height> has higher difficulty (<new> > <old>)
⚠️  FORK DETECTED - Heavier chain wins but balance reorg not yet implemented
```

**Fork detected (equal difficulty)**:
```
🔀 [FORK RESOLUTION] Tie on difficulty, choosing block from proposer <id> (lower ID)
⚠️  FORK DETECTED - Same difficulty, lower proposer ID wins
```

**Fork rejected (lighter incoming)**:
```
🔀 [FORK RESOLUTION] Rejecting lighter fork at height <height> (<incoming> < <existing>)
```

### Manual Actions Required

When you see fork warnings:
1. Note the block height where fork occurred
2. Identify miners in both forks
3. Calculate expected balances for each miner
4. Compare with actual balances
5. If discrepancies found, manual balance correction needed
