# v0.9.102-beta: Hardcoded Phase 5 Network ID Fix

## Deployment Date
2025-11-11 16:00 UTC (pending)

## Problem Statement

The `/api/v1/status` endpoint was returning **hardcoded Phase 5 metadata** instead of reading the actual `Q_NETWORK_ID` environment variable. This caused:

1. **Bootstrap Discovery Failure**: Fresh nodes querying the bootstrap server would receive Phase 5 network metadata but were expecting Phase 10
2. **Network Isolation**: Nodes couldn't connect because of network ID mismatch
3. **Manual Restart Required**: Only workaround was to restart the service to refresh network connections

## Root Cause

### Location 1: Bootstrap Status Endpoint
**File**: `crates/q-api-server/src/handlers.rs`
**Lines**: 379-380

```rust
// v0.9.101-beta (BROKEN)
"network_id": "testnet-phase5",  // ❌ Hardcoded Phase 5
"version": "v0.9.3-beta",        // ❌ Hardcoded old version
```

### Location 2: P2P Health Status
**File**: `crates/q-api-server/src/handlers.rs`
**Lines**: 1999-2002

```rust
// v0.9.101-beta (BROKEN)
gossipsub_topics: vec![
    "/qnk/testnet-phase5/blocks".to_string(),              // ❌ Hardcoded Phase 5
    "/qnk/testnet-phase5/peer-heights".to_string(),       // ❌ Hardcoded Phase 5
    "/qnk/testnet-phase5/block-pack-requests".to_string(), // ❌ Hardcoded Phase 5
    "/qnk/testnet-phase5/block-pack-responses".to_string(), // ❌ Hardcoded Phase 5
],
```

**Impact**:
- Nodes looking for Phase 10 bootstrap info would get Phase 5 data
- Network ID mismatch prevents libp2p peer discovery
- Fresh nodes couldn't automatically discover and connect to the network

## Solution Implemented (v0.9.102-beta)

### Fix 1: Read Network ID from Environment Variable

**File**: `crates/q-api-server/src/handlers.rs`
**Line 379**:

```rust
// v0.9.102-beta (FIXED)
"network_id": std::env::var("Q_NETWORK_ID").unwrap_or_else(|_| "testnet-phase10".to_string()),
"version": "v0.9.102-beta",
```

**Explanation**:
- Reads `Q_NETWORK_ID` environment variable (set in systemd service to "testnet-phase10")
- Falls back to "testnet-phase10" if not set
- Updates version to current release

### Fix 2: Dynamic Gossipsub Topic Construction

**File**: `crates/q-api-server/src/handlers.rs`
**Lines 1994-2005**:

```rust
// v0.9.102-beta (FIXED)
// Get network ID for gossipsub topics
let network_id = std::env::var("Q_NETWORK_ID").unwrap_or_else(|_| "testnet-phase10".to_string());

let health = P2PHealthStatus {
    libp2p_manager_active: state.libp2p_discovery.is_some(),
    connected_peers: libp2p_peers,
    turbo_sync_available,
    gossipsub_topics: vec![
        format!("/qnk/{}/blocks", network_id),
        format!("/qnk/{}/peer-heights", network_id),
        format!("/qnk/{}/block-pack-requests", network_id),
        format!("/qnk/{}/block-pack-responses", network_id),
    ],
    network_status,
    current_height,
    network_height,
    sync_progress_percent,
    bootstrap_peer_configured,
};
```

**Explanation**:
- Dynamically constructs gossipsub topic names using actual network ID
- Ensures reported topics match what the node is actually listening on
- Allows easy phase transitions without code changes

## Lessons Learned

1. **Never Hardcode Network Configuration**: Always read from environment variables or config files
2. **Phase Transitions Need Dynamic Config**: Hardcoded phase identifiers cause network fragmentation
3. **API Responses Must Match Reality**: Incorrect metadata breaks discovery and debugging
4. **Environment Variables Need Validation**: Always verify systemd service has correct env vars set
5. **Bootstrap Discovery is Critical**: Any mismatch in bootstrap metadata breaks fresh node onboarding
