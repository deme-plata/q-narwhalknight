## Changes

### 🚀 Fix: Consistent Mining Challenges During Sync

**Problem Solved**: "Messy height changes" causing mining confusion

**Root Cause**:
- Turbo Sync binary search correctly finds highest contiguous block
- Gossipsub delivers blocks out-of-order (normal P2P behavior)
- Height progression skipped missing blocks: 1829→1831 (missing 1830)
- Miners received different challenges for different heights
- Result: Confusion about which block to mine

**Fix Applied**:
```rust
// BEFORE (v0.7.3-beta):
let block_height = state.node_status.read().await.current_height;
let challenge_data = format!("block_{}_time_{}", block_height, ...);

// AFTER (v0.7.4-beta):
let current_height = state.node_status.read().await.current_height;
let block_height = current_height + 1;  // Always mine for NEXT block
let challenge_data = format!("block_{}_time_{}", block_height, ...);
```

**Impact**:
- ✅ Miners always target the NEXT expected block
- ✅ Consistent challenges regardless of sync state
- ✅ No more confusion from height "jumps"
- ✅ Clean mining experience

**File Modified**: `crates/q-api-server/src/handlers.rs:4149-4157`

## Technical Details

### How It Works

**Before (v0.7.3-beta)**:
```
Current height: 1829
Mining challenge: "block_1829_time_..."
---
Height jumps to 1831 (1830 missing due to gossipsub delay)
Mining challenge: "block_1831_time_..." ❌ Different challenge!
Miners confused: "Was mining 1829, now 1831? Where's 1830?"
```

**After (v0.7.4-beta)**:
```
Current height: 1829
Mining challenge: "block_1830_time_..." (always next)
---
Height jumps to 1831 (1830 missing)
Mining challenge: "block_1832_time_..." (still always next)
Miners happy: "Mining for next block, height changes don't affect me"
```

### Why This Works

1. **Miners don't care about current height**, they care about NEXT block
2. **Challenges are now stable** - always target `current_height + 1`
3. **Binary search can skip heights** without confusing miners
4. **Missing blocks eventually arrive** and fill gaps automatically
