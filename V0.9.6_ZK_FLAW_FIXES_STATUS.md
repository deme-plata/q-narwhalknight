### Flaw #2: Mock ZK-STARK Proofs (🔴 CRITICAL)
**Location**: `crates/q-network/src/zk_peer_height_proof.rs:215-237`

**Issue**: Current implementation generates mock proofs that prove nothing:
```rust
pub async fn generate_height_proof(
    stark_system: &mut StarkSystem,
    block: &QBlock,
) -> Result<StarkProof> {
    // This is MOCK data - not a real ZK-STARK proof!
    let trace = vec![
        vec![block.header.height],
        vec![u64::from_le_bytes(block.hash[..8].try_into()?)],
    ];
    let constraints = b"block_possession_circuit_v1";
    let proof = stark_system.prove(&trace, constraints).await?;
}
```

**Root Cause**:
1. ❌ No blockchain state circuit defined
2. ❌ Trace is just raw u64 values, not proper execution trace
3. ❌ Constraints are byte string, not AIR polynomial constraints
4. ❌ Doesn't actually prove block possession

**Security Impact**:
- Any peer can generate "valid" proofs for blocks they don't have
- Entire ZK-STARK height verification is security theater
- Verifier will accept ANY proof

**Fix Required**: Create proper blockchain state circuit in `q-zk-stark`:
```rust

}

impl BlockPossessionCircuit {
    pub fn generate_trace(&self) -> Vec<Vec<u64>> {
        // Create REAL execution trace proving:
        // 1. You know block_hash
        // 2. block_hash is at claimed height
        // 3. Merkle path from block_hash to merkle_root is valid
    }

    pub fn generate_constraints(&self) -> AIRConstraints {
        // Create polynomial constraints verifying:
        // 1. Hash computation correctness
        // 2. Merkle path verification
        // 3. Height consistency
    }
}
```

### Flaw #3: Rate Limiter Lock Holding (🔴 CRITICAL)
**Location**: `crates/q-storage/src/zk_block_request_auth.rs:114-139`

**Issue**: Rate limiter holds write lock for entire function duration:
```rust
pub async fn check_rate_limit(&self, peer_id: &PeerId) -> Result<bool> {
    let mut rate_limiter = self.rate_limiter.write().await;  // Lock acquired

    // ... do work ...

    if entry.0 >= self.max_requests_per_minute {
        return Ok(false);  // Lock released here
    }

    entry.0 += 1;
    Ok(true)  // Or here
}
```

**Problem**: While this specific implementation doesn't deadlock, it's inefficient:
- Write lock held for entire function
- Blocks all other rate limit checks
- Could use RwLock::read() first, only upgrade to write when needed

**Fix Required**: Optimize lock strategy:
```rust
pub async fn check_rate_limit(&self, peer_id: &PeerId) -> Result<bool> {
    let now = Instant::now();

    // First, try read-only check (most common case)
    {
        let rate_limiter = self.rate_limiter.read().await;
        if let Some((count, last_reset)) = rate_limiter.get(peer_id) {
            // If within same minute window and not at limit
            if now.duration_since(*last_reset).as_secs() < 60
                && *count < self.max_requests_per_minute {
                // Can fast-path with just a read lock? NO - need to increment
            }
        }
    }

    // Need write lock to modify
    let mut rate_limiter = self.rate_limiter.write().await;
    // ... do actual update ...
}
```

**Better Fix**: Use atomic counters or lock-free data structures

### Bug #4: Memory Leak in Reputation HashMap (🟠 HIGH)
**Location**: `crates/q-network/src/zk_peer_height_proof.rs:86-100`

**Issue**: `peer_reputation` HashMap grows unbounded:
```rust
peer_reputation: Arc<RwLock<HashMap<PeerId, (u64, u64)>>>,
```

**Problem**:
- Every peer that ever connects gets an entry
- Entries never removed
- After weeks: millions of stale peer entries
- Memory grows infinitely

**Fix Required**: Add cleanup task:
```rust
/// Cleanup old reputation entries (every 24 hours)
async fn cleanup_old_reputation(&self) {
    let mut reputation = self.peer_reputation.write().await;
    let cutoff = SystemTime::now() - Duration::from_secs(86400 * 7); // 7 days

    reputation.retain(|peer_id, (successful, failed)| {
        // Keep if recently active OR has high reputation
        recently_seen(peer_id) || (*successful > 100 && *failed < 10)
    });

    info!("🧹 Cleaned up {} stale reputation entries", removed_count);
}
```

### Bug #5: Non-Persistent Banned Peers (🟠 HIGH)
**Location**: `crates/q-network/src/zk_peer_height_proof.rs:89`

**Issue**: Banned peers list only in memory:
```rust
banned_peers: Arc<RwLock<std::collections::HashSet<PeerId>>>,
```

**Problem**:
- Node restart = all bans lost
- Attackers can reconnect after node restart
- Ban evasion is trivial

**Fix Required**: Persist to database:
```rust
// Store in RocksDB under "banned_peers" column family
pub async fn ban_peer(&self, peer_id: &PeerId) {
    // 1. Add to in-memory set
    self.banned_peers.write().await.insert(*peer_id);

    // 2. Persist to database
    let ban_record = BanRecord {
        peer_id: *peer_id,
        banned_at: SystemTime::now(),
        reason: "Invalid ZK proof",
        expires_at: None,  // Permanent ban
    };
    self.db.put_cf("banned_peers", peer_id.as_bytes(), &bincode::serialize(&ban_record)?)?;

    // 3. Disconnect peer if currently connected
    self.swarm.disconnect_peer_id(*peer_id);
}
```

For testnet deployment, this is acceptable as we're testing the integration architecture, not relying on cryptographic security properties yet.
