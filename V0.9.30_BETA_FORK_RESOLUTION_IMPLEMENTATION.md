# v0.9.30-beta: Fork Resolution Implementation

## Problem Statement

**Server Alpha** (161.35.219.10) and **Server Beta** (185.182.185.227) are both mining independently, creating blockchain forks:
- Both servers produce blocks at the same height
- When Server Alpha's blocks arrive at Server Beta via gossipsub, they are rejected because Server Beta already has a block at that height
- Result: Mining rewards from Server Alpha never sync to Server Beta

## Root Cause

The gossipsub block handler (`crates/q-api-server/src/main.rs` lines 2004-2051) was checking if a block already exists at a height and **immediately rejecting** duplicates without comparing cumulative difficulty:

```rust
// OLD BEHAVIOR (v0.9.29 and earlier)
match storage.get_qblock_by_height(block_height).await {
    Ok(Some(_)) => {
        // Block already exists - skip saving (duplicate from gossipsub)
        return;  // ❌ WRONG: Rejects heavier forks!
    }
    // ...
}
```

This prevented **fork resolution** - the network couldn't choose the canonical chain when forks occurred.

## Solution: Fork-Choice Rule Based on Cumulative Difficulty

Implemented a **fork-choice rule** that compares cumulative difficulty (total proof-of-work) to resolve forks:

### Algorithm

1. **Compare cumulative difficulty** (`total_difficulty` field in `BlockHeader`)
   - If incoming block has **higher difficulty** → Accept (heavier chain wins)
   - If incoming block has **lower difficulty** → Reject (keep existing block)
   - If **equal difficulty** → Use proposer ID as tiebreaker (lower ID wins)

2. **Deterministic tiebreaker**: When difficulties are equal, use `block.header.proposer` comparison
   - Ensures all nodes make the same choice
   - Prevents network splits

### Implementation

**File**: `crates/q-api-server/src/main.rs` (lines 1999-2044)

```rust
// v0.9.30-beta: FORK-CHOICE RULE - Heaviest chain wins
match storage.get_qblock_by_height(block_height).await {
    Ok(Some(existing_block)) => {
        // 🔀 FORK DETECTED
        let existing_difficulty = existing_block.header.total_difficulty;
        let incoming_difficulty = block.header.total_difficulty;

        if incoming_difficulty > existing_difficulty {
            // 🚀 HEAVIER CHAIN wins
            warn!("🔀 [FORK RESOLUTION] Incoming block {} has higher difficulty ({} > {})",
                  block_height, incoming_difficulty, existing_difficulty);
            // Fall through to normal processing (will overwrite existing block)
        } else if incoming_difficulty == existing_difficulty {
            // 🟰 TIE - use proposer ID tiebreaker
            if block.header.proposer < existing_block.header.proposer {
                warn!("🔀 [FORK RESOLUTION] Tie - choosing block from proposer {} (lower ID)",
                      hex::encode(&block.header.proposer[..4]));
                // Fall through to processing
            } else {
                return; // Keep existing block
            }
        } else {
            // ⬇️ LIGHTER CHAIN - reject
            debug!("🔀 [FORK RESOLUTION] Rejecting lighter fork");
            return;
        }
    }
    Ok(None) => {
        // No conflict - proceed normally
    }
}
```

## Current Status: ⚠️ PARTIAL IMPLEMENTATION

### ✅ What Works
- Fork detection and comparison logic
- Heaviest chain wins
- Deterministic tiebreaker
- Block storage will overwrite lighter fork with heavier fork

### ⚠️ Known Limitation: Balance Reorg Not Implemented

**The current implementation will:**
1. ✅ Overwrite the block in storage with the heavier fork
2. ❌ **NOT adjust balances** to reflect the fork switch

**Example scenario:**
- Server Beta mines block 12345 → Miner B gets 0.001 QNK
- Server Alpha mines block 12345 (heavier) → Miner A should get 0.001 QNK
- **Current behavior:**
  - Block 12345 is replaced with Server Alpha's version ✅
  - Miner B keeps their 0.001 QNK ❌ (should be removed)
  - Miner A does NOT get 0.001 QNK ❌ (should be added)

### Why Balance Reorg Is Challenging

The balance consensus engine (`crates/q-storage/src/balance_consensus.rs`) prevents double-processing using a block hash cache:

```rust
// Each block hash can only be processed once
let block_hash = self.calculate_block_hash(block);
if processed.contains(&block_hash) {
    return Err(AlreadyProcessed(block_hash));
}
```

For a proper chain reorganization, we would need to:

1. **Roll back old block's rewards:**
   - Subtract mining rewards from old block's miner
   - Subtract dev fee from FOUNDER_WALLET

2. **Apply new block's rewards:**
   - Add mining rewards to new block's miner
   - Add dev fee to FOUNDER_WALLET

3. **Handle edge cases:**
   - Same miner in both blocks (net zero change)
   - Different reward amounts (due to timestamp differences)
   - Multiple forks in a row

**Current workaround**: Manual balance correction required when forks occur.

## Security Considerations

1. **Attack vector: Difficulty manipulation**
   - Mitigation: `total_difficulty` is cumulative from genesis, extremely expensive to fake

2. **Attack vector: Timestamp manipulation**
   - Current: Block rewards based on timestamp (halving schedule)
   - Mitigation needed: Network time validation

3. **Attack vector: Fork spam**
   - Risk: Attacker creates many forks to trigger balance reorg repeatedly
   - Mitigation: Rate limit fork resolution per peer
