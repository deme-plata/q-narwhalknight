## What Was Fixed

### 🚨 Critical Discovery

The root cause was **NOT** in the BlockWriter logic, but in the **KVStore trait implementation**:

**BEFORE (v0.9.92-beta)**:
```rust
// ❌ UNSAFE - No sync!
async fn put(&self, cf: &str, key: &[u8], value: &[u8]) -> Result<()> {
    self.db.put_cf(&cf_handle, key, value)?; // NO FSYNC!
    Ok(())
}
```

**AFTER (v0.9.93-beta)**:
```rust
// ✅ SAFE - Always synced!
async fn put(&self, cf: &str, key: &[u8], value: &[u8]) -> Result<()> {
    let mut write_opts = rocksdb::WriteOptions::default();
    write_opts.set_sync(true);        // Force fsync()
    write_opts.disable_wal(false);    // Keep WAL enabled

    self.db.put_cf_opt(&cf_handle, key, value, &write_opts)?;

    debug!("💾 Synced put: cf={}, key_len={}", cf, key.len());
    Ok(())
}
```

**Same fix applied to `.delete()` method.**

## Key Insights

### 1. The Real Problem
**Not** parallel write conflicts (BlockWriter fixed that)
**But** unsync'd writes in `.put()` and `.delete()` methods

### 2. Why v0.7.3's Fix Didn't Work
- `write_batch()` had sync=true ✅
- BUT `.put()` did NOT have sync=true ❌
- Code paths using `.put()` were vulnerable

### 3. What This Means
- DAG vertices could be lost on kill -9
- Payloads could be lost on kill -9
- Certificates could be lost on kill -9
- **Blocks were probably safe** (used write_batch)
- But corruption could cascade from DAG data loss

### 4. Why It Took 11 Occurrences
- Only happened when:
  1. Write occurred
  2. Kill -9 happened BEFORE fsync
  3. WAL not flushed
  4. OS cache not written
- **Probability**: ~5-10% per restart
- **11 occurrences over 6 months** fits this model
