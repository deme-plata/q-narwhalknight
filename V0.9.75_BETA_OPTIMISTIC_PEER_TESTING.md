# v0.9.75-beta: Optimistic Peer Testing - Sync Performance Fix

## Release Date
2025-11-09

## Critical Fix: 200x Sync Speed Improvement

### Problem Identified
**Chicken-and-Egg Peer Compatibility Deadlock**

The BlockPackCodec sync system had a fatal circular dependency:
1. Peers were only marked "compatible" AFTER successfully responding to BlockPack requests
2. BlockPack requests were ONLY sent to "compatible" peers
3. Result: New peers were NEVER tested, NEVER marked compatible, NEVER received requests

### Impact
- Server Alpha: Syncing at ~5 blocks/few minutes (~60 blocks/hour)
- Expected: 2000+ blocks/10 seconds (~12,000 blocks/minute)
- **Actual slowdown**: ~200x slower than designed capacity

### Root Cause Code

```rust
// BEFORE (v0.9.73-beta) - BROKEN LOGIC:
let mut top_peers: Vec<_> = peer_registry.iter()
    .filter(|(peer_id, height)| {
        // ❌ PROBLEM: Only use peers already proven compatible
        compatible_peers.contains(peer_id) && *height >= network_height
    })
    .collect();

// Result: compatible_peers list starts EMPTY
// → No peers selected
// → No requests sent
// → No peers become compatible
// → Infinite deadlock loop
```

### Fix Implementation

```rust
// AFTER (v0.9.75-beta) - OPTIMISTIC TESTING:
let blacklisted_peers = libp2p_lock.get_blacklisted_peers();

let mut top_peers: Vec<_> = peer_registry.iter()
    .filter(|(peer_id, height)| {
        // ✅ OPTIMISTIC: Use ALL peers EXCEPT proven incompatible
        !blacklisted_peers.contains(peer_id) && *height >= network_height
    })
    .collect();

// Result: All new peers are tested immediately
// → Requests sent on first contact
// → Compatible peers respond successfully
// → Incompatible peers fail 3x → blacklisted
// → System learns peer compatibility through testing
```

## Changes in v0.9.75-beta

### 1. Optimistic Peer Testing (Critical)

**File**: `crates/q-api-server/src/main.rs`

**Before**: Only send BlockPack requests to pre-verified "compatible" peers
**After**: Send requests to ALL peers except proven-incompatible (blacklisted) peers

**Logic Change**:
- **Old**: `compatible_peers.contains(peer_id)` (whitelist approach)
- **New**: `!blacklisted_peers.contains(peer_id)` (blacklist approach)

**Benefits**:
- Eliminates chicken-and-egg deadlock
- New peers tested immediately on first contact
- Fast failure detection (3 failures → blacklist)
- Self-healing peer discovery

### 2. Enhanced Debugging Logs

**Added comprehensive logging**:

**Purpose**: Diagnose why requests aren't being sent/received

**File**: `crates/q-api-server/src/main.rs:5086`

**Reason**: Account for network latency in initial peer testing

### 4. New Network Manager Method

**File**: `crates/q-network/src/unified_network_manager.rs`

**Added**: `get_blacklisted_peers()` method

```rust
/// v0.9.75-beta: Get list of blacklisted peers (proven incompatible after 3+ failures)
/// Used for OPTIMISTIC peer testing - assume compatible unless blacklisted
pub fn get_blacklisted_peers(&self) -> std::collections::HashSet<PeerId> {
    let compat = self.peer_compat.read().unwrap();
    compat.blacklist.clone()
}
```

**Purpose**: Provide efficient blacklist checking for optimistic filtering

## Peer Compatibility Lifecycle

### New Peer Discovery Flow:

```
1. Peer discovered via gossipsub (announces height)
   ↓
2. Added to peer_registry with height
   ↓
3. Sync system checks: height >= network_height?
   ↓
4. Check blacklist: is peer blacklisted?
   ↓
5. If NOT blacklisted → SEND BlockPack request (OPTIMISTIC)
   ↓
6a. Success → Peer marked compatible (success counter++)
6b. Failure → Failure counter++
   ↓
7. If failures >= 3 → ADD TO BLACKLIST
   ↓
8. Blacklisted peers excluded from future requests
```

### Key Insight:
**Trust by default, blacklist on failure** is MUCH faster than **distrust by default, whitelist on success**
