## Critical Fixes Implemented

### 1. Wallet Balance Loss Race Condition (CRITICAL)

**Severity**: CRITICAL
**Impact**: Users losing ~50 QNK coins on every restart
**Root Cause**: Lost update race condition in wallet balance persistence

#### Problem
The mining reward system had a classic "lost update" race condition:
- Memory update happened INSIDE lock (fast)
- Lock was dropped BEFORE disk persistence
- Disk persistence happened AFTER lock drop (slow, async)
- Other threads could read stale data from disk between memory update and persistence

#### Solution
Changed persistence order to persist BEFORE dropping lock in both locations:

**Location 1**: `main.rs:1348-1361` (Mining batch processor)
**Location 2**: `main.rs:1827-1831` (Network gossip receiver)

Both now follow safe pattern:
1. Lock acquired
2. Update memory
3. **Persist to disk (while holding lock)**
4. Drop lock

#### Error 3: Missing Variable - pending_loan_applications_map
**File**: `lib.rs:1682`
**Problem**: Second AppState constructor missing loan loading logic
**Fix**: Added loan loading logic at lines 1461-1490
```rust
// Load existing loan applications from persistent storage
let mut pending_loan_applications_map = HashMap::new();
match storage_engine.load_loan_applications().await {
    Ok(persisted_loans) => {
        for (loan_id, loan_bytes) in persisted_loans {
            match bincode::deserialize::<crate::quillon_bank_api::LoanApplication>(&loan_bytes) {
                Ok(loan) => {
                    pending_loan_applications_map.insert(loan_id.clone(), loan);
                }
                Err(e) => {
                    tracing::warn!("Failed to deserialize loan application {}: {}, skipping", loan_id, e);
                }
            }
        }
        tracing::info!("🏦 Loaded {} loan applications from persistent storage", pending_loan_applications_map.len());
    }
    Err(e) => {
        tracing::warn!("Failed to load loan applications from storage: {}, starting with empty loans", e);
    }
}
```

### 3. Type Mismatch in Loan Application Storage

**File**: `quillon_bank_api.rs:774`
**Problem**: Type mismatch when inserting into HashMap - crate compiled multiple times
**Fix**: Reordered operations to persist/broadcast BEFORE inserting into HashMap

Changed operation order from:
1. Insert into HashMap (clone)
2. Persist to RocksDB
3. Broadcast to network

To:
1. Persist to RocksDB
2. Broadcast to network
3. Insert into HashMap (consume, no clone needed)

This avoids the type mismatch because `loan_application` is moved into the HashMap as the final operation.
