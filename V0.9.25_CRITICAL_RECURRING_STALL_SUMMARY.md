# v0.9.25-beta CRITICAL: Recurring Block Producer Stalls

**Date**: 2025-11-06 08:31 CET
**Severity**: CRITICAL - Production Blocking
**Status**: Phase 5 network unstable due to recurring stalls

---

## 🚨 EXECUTIVE SUMMARY

**v0.9.25-beta has a CRITICAL recurring bug that makes it unsuitable for production deployment.**

The block producer stalls every 6-17 minutes when serving large TurboSync batches (300+ blocks). While the system may auto-recover after 60 seconds, this creates an unreliable network experience.

**Recommendation**: Hold v0.9.25-beta deployment, prioritize v0.9.26-beta with TurboSync fixes.

## 🔬 ROOT CAUSE ANALYSIS

### **Confirmed Pattern**:
1. Peer requests large TurboSync batch (300+ blocks)
2. Block producer loads and serializes blocks
3. Heavy I/O operation blocks tokio runtime
4. Block producer task unable to acquire resources
5. Watchdog detects 60-second stall
6. System may auto-recover or require manual restart

## 💡 IMMEDIATE FIXES REQUIRED FOR v0.9.26-beta

### **1. Batch Size Limits** (CRITICAL)
**File**: `crates/q-api-server/src/main.rs` (TurboSync request handler)

```rust
// Add at top of turbo_sync request handler
const MAX_BATCH_SIZE: u64 = 100; // Prevent stalls

if end_height - start_height > MAX_BATCH_SIZE {
    warn!("🚧 Large batch request ({} blocks) - splitting into chunks",
          end_height - start_height);
    end_height = start_height + MAX_BATCH_SIZE;
}
```

**Rationale**:
- 319 and 453 block batches caused stalls
- Limit to 100 blocks per batch
- Multiple smaller batches won't block tokio runtime

### **2. Async TurboSync Task Spawning** (CRITICAL)
**File**: `crates/q-api-server/src/main.rs` (TurboSync send logic)

```rust
// Don't block block producer on TurboSync
let storage_clone = storage.clone();
tokio::spawn(async move {
    match turbo_sync_send_blocks(storage_clone, peer_id, start, end).await {
        Ok(_) => info!("✅ Sent TurboSync batch {}-{}", start, end),
        Err(e) => error!("❌ TurboSync batch failed: {}", e),
    }
});
```

**Rationale**:
- Isolate TurboSync from block producer
- Prevent I/O blocking on main tokio runtime
- Allow concurrent TurboSync and block production

### **3. Block Producer Health Monitoring** (HIGH)
**File**: `crates/q-api-server/src/block_producer.rs`

```rust
// Publish health metrics every 10 seconds
metrics::gauge!("block_producer.last_block_time", last_block_timestamp);
metrics::gauge!("block_producer.height", current_height);
metrics::counter!("block_producer.stalls", stall_count);
```

**Rationale**:
- Early detection of stalls
- Prometheus metrics for monitoring
- Better observability

### **4. TurboSync Rate Limiting** (MEDIUM)
**File**: `crates/q-api-server/src/main.rs`

```rust
// Track TurboSync requests per peer
let mut turbo_sync_limiter = HashMap::new();

if let Some(last_request) = turbo_sync_limiter.get(&peer_id) {
    if last_request.elapsed() < Duration::from_secs(5) {
        warn!("🚧 TurboSync rate limit: peer {} too fast", peer_id);
        return; // Drop request
    }
}
turbo_sync_limiter.insert(peer_id, Instant::now());
```

**Rationale**:
- Prevent rapid TurboSync requests
- Limit concurrent batch operations
- Reduce resource contention

## 📝 LESSONS LEARNED

### **What Went Wrong**:
1. **No batch size limits** - Allowed 300+ block batches
2. **Blocking I/O in async context** - TurboSync blocked tokio runtime
3. **Insufficient testing** - Did not test large batch scenarios
4. **No production monitoring** - Watchdog only detection mechanism

### **What Went Right**:
1. **Watchdog detection** - Caught stalls within 60 seconds
2. **No data loss** - Blockchain integrity maintained
3. **Auto-recovery observed** - System can recover without restart
4. **Comprehensive logging** - Easy root cause identification

### **Process Improvements**:
1. **Load testing required** - Test with 1000+ block syncs
2. **Performance benchmarking** - Measure TurboSync latency
3. **Staging environment** - Test with multiple peers before production
4. **Monitoring setup** - Prometheus + Grafana before deployment
