# v0.8.1-beta Atomic Transactions Design

**Date**: 2025-11-02
**Issue**: CRITICAL-1 from Security Audit
**Purpose**: Fix race condition between balance updates and block storage

---

## Problem Statement

### Current Issue (CRITICAL-1)

Balance updates and block storage happen in **two separate operations**:

```rust
// Step 1: Update balances (committed to disk)
balance_engine.process_block_mining_rewards(&storage, &block).await?;

// Step 2: Save block (separate operation)
storage.save_qblock(&block).await?;
```

**Attack Scenario**:
1. Node processes balance consensus (balances updated ✅)
2. Node crashes before saving block ❌
3. On restart: Balances exist but block missing
4. Block hash already in `processed_blocks` HashMap
5. Reprocessing returns `AlreadyProcessed`
6. **Result**: Miner loses reward permanently, consensus fails

---

## Solution Design

### Atomic Transaction API

Add transaction support to QStorage that ensures **both operations succeed or both fail**:

```rust
// NEW API: Atomic transaction
let tx = storage.begin_transaction().await?;

// Step 1: Process balance consensus (not yet committed)
let updates = balance_engine.process_block_mining_rewards_tx(&tx, &block).await?;

// Step 2: Save block (not yet committed)
tx.save_qblock(&block).await?;

// Step 3: Commit atomically (all or nothing)
tx.commit().await?;
```

### Transaction Lifecycle

```
┌─────────────────┐
│ begin_transaction│
└────────┬─────────┘
         │
         ▼
┌─────────────────┐     Crash?     ┌─────────────┐
│  Write Operations│────────────────►│  Rollback   │
│  (in WriteBatch) │                │ (Automatic) │
└────────┬─────────┘                └─────────────┘
         │
         ▼
┌─────────────────┐     Crash?     ┌─────────────┐
│     commit()     │────────────────►│  Rollback   │
└────────┬─────────┘                │ (Automatic) │
         │                          └─────────────┘
         ▼
┌─────────────────┐
│ Success (Atomic) │
└─────────────────┘
```

**Key Properties**:
- **Atomicity**: All writes succeed or all fail
- **Durability**: After commit(), data is guaranteed on disk
- **Isolation**: Each transaction is independent
- **Crash Safety**: If crash before commit(), nothing is written

## Implementation Components

### 1. QTransaction Struct

```rust
/// Atomic transaction wrapper for QStorage operations
///
/// **SECURITY FIX (v0.8.1-beta)**: Implements atomic transactions to prevent
/// race condition between balance updates and block storage (CRITICAL-1)
///
/// Usage:
/// ```rust
/// let tx = storage.begin_transaction().await?;
/// tx.save_qblock(&block).await?;
/// balance_engine.process_block_mining_rewards_tx(&tx, &block).await?;
/// tx.commit().await?;  // All or nothing
/// ```
pub struct QTransaction {
    /// RocksDB write batch for atomic operations
    write_batch: Arc<Mutex<rocksdb::WriteBatch>>,

    /// Reference to hot database
    hot_db: Arc<RocksDBKV>,

    /// Reference to cold database
    cold_db: Arc<RocksDBKV>,

    /// Transaction state
    state: Arc<Mutex<TransactionState>>,

    /// Balance updates (for rollback tracking)
    balance_updates: Arc<Mutex<Vec<BalanceUpdate>>>,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum TransactionState {
    Active,     // Transaction in progress
    Committed,  // Successfully committed
    Aborted,    // Rolled back or failed
}
```

### 2. Transaction Methods

```rust
impl QTransaction {
    /// Save block to storage (buffered in transaction)
    pub async fn save_qblock(&self, block: &QBlock) -> Result<()>;

    /// Apply balance update (buffered in transaction)
    pub async fn apply_balance_update(&self, update: &BalanceUpdate) -> Result<()>;

    /// Commit all changes atomically
    pub async fn commit(self) -> Result<()>;

    /// Rollback all changes (called automatically on drop if not committed)
    pub async fn rollback(self) -> Result<()>;
}
```

## RocksDB WriteBatch Implementation

### WriteBatch Benefits

RocksDB's `WriteBatch` provides:
- **Atomicity**: All writes in batch succeed or fail together
- **Performance**: Batch writes are faster than individual writes
- **Durability**: Single fsync after all writes
- **Crash Safety**: WAL (Write-Ahead Log) ensures recovery

### Implementation

```rust
impl QTransaction {
    pub async fn commit(mut self) -> Result<()> {
        let mut state = self.state.lock().await;
        if *state != TransactionState::Active {
            return Err(anyhow!("Transaction already completed"));
        }

        // Get write batch
        let batch = self.write_batch.lock().await;

        // Atomic commit to RocksDB with sync=true for durability
        let write_options = rocksdb::WriteOptions::default();
        write_options.set_sync(true);  // fsync before returning

        self.hot_db.write_batch(&batch, Some(&write_options)).await?;

        // Mark as committed
        *state = TransactionState::Committed;

        info!("✅ Transaction committed atomically");
        Ok(())
    }
}
```

async fn test_transaction_atomicity() {
    let storage = QStorage::new_test().await.unwrap();

async fn test_transaction_rollback_on_failure() {
    let storage = QStorage::new_test().await.unwrap();

    // Add operations
    tx.save_qblock(&block1).await.unwrap();

## Performance Impact

### WriteBatch Performance

**Before** (2 separate writes):
- Write balance updates: 1-2ms
- Write block: 1-2ms
- **Total**: 2-4ms per block

**After** (1 atomic write):
- Batch all operations: ~2-3ms
- **Total**: 2-3ms per block

**Improvement**: ~25% faster due to single fsync

### Memory Overhead

- WriteBatch memory: ~1-2 KB per transaction
- Negligible overhead compared to block size (10-100 KB)
