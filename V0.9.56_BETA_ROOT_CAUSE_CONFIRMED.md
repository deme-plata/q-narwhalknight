# v0.9.56-beta: ROOT CAUSE CONFIRMED - Version Mismatch

## 🎯 CRITICAL FINDING

**Root Cause**: Server Beta is sending **OLD format** BlockPackRequests (without `protocol_version` field), while Server Alpha is trying to decode them as **NEW format** (with `protocol_version` field).

---

## Evidence from Server Alpha Logs (161.35.219.10)

Source: `looksgoodbutslow57.txt` from latest beta build

### Corruption Pattern

Multiple corrupted requests received, all following the same pattern:

```
Line 1024: start_height=1762593084, Raw: [188, 146, 188, 200, 6, 52, 49, 50, 68, ...]
Line 1182: start_height=1762593089, Raw: [193, 146, 188, 200, 6, 52, 49, 50, 68, ...]
Line 1224: start_height=1762593094, Raw: [198, 146, 188, 200, 6, 52, 49, 50, 68, ...]
Line 1250: start_height=1762593099, Raw: [203, 146, 188, 200, 6, 52, 49, 50, 68, ...]
Line 1292: start_height=1762593104, Raw: [208, 146, 188, 200, 6, 52, 49, 50, 68, ...]
```

**Key Observations**:
1. Corrupted heights increment by ~5 each time
2. First byte increments: 188 → 193 → 198 → 203 → 208 (increment of 5)
3. Remaining bytes are IDENTICAL: `[146, 188, 200, 6, 52, 49, 50, 68, ...]`
4. Bytes `52, 49, 50, 68, 51, 75, 111, 111, 87` = ASCII `"412D3KooW"` (start of Peer ID!)

## Byte-Level Analysis

### Corrupted Decoding

```python
Raw bytes: [188, 146, 188, 200, 6, 52, 49, 50, 68, 51, 75, 111, 111, 87]

Varint 1: 1762593084 (5 bytes: [188, 146, 188, 200, 6])
  ↑ This is being decoded as start_height (WRONG!)
  ↑ This is actually part of the REQUEST_ID string!

Varint 2: 52 (1 byte: [52])
  ↑ ASCII '4' - first character of "412D3KooW..."

Remaining: [49, 50, 68, 51, 75, 111, 111, 87]
  ↑ ASCII: "12D3KooW" - continuation of Peer ID
```

### What This Proves

The decoder is reading the **request_id string as start_height**!

This happens when:
- **Sender** (Server Beta) sends: `[start_height, end_height, request_id]` (OLD format, 3 fields)
- **Receiver** (Server Alpha) expects: `[protocol_version, start_height, end_height, request_id]` (NEW format, 4 fields)
- Due to struct field misalignment, postcard reads `start_height` as `protocol_version`, and `request_id` as `start_height`

## Why This Happens

### Scenario 1: Server Beta Has OLD Binary (v0.9.52 or earlier)

**Server Beta binary** has this struct (WITH `#[serde(default)]`):
```rust
#[derive(Serialize, Deserialize)]
pub struct BlockPackRequest {
    #[serde(default)]  // ❌ BUG: Causes postcard to skip this field!
    pub protocol_version: u32,
    pub start_height: u64,
    pub end_height: u64,
    pub request_id: String,
}
```

When serializing:
```rust
// postcard SKIPS protocol_version due to #[serde(default)]
// Produces: [start_height, end_height, request_id]  (3 fields)
```

**Server Alpha binary** has this struct (WITHOUT `#[serde(default)]`):
```rust
#[derive(Serialize, Deserialize)]
pub struct BlockPackRequest {
    pub protocol_version: u32,  // ✅ No #[serde(default)]
    pub start_height: u64,
    pub end_height: u64,
    pub request_id: String,
}
```

When deserializing:
```rust
// Expects 4 fields: [protocol_version, start_height, end_height, request_id]
// Receives 3 fields: [start_height, end_height, request_id]
// Result: Field misalignment!
//   - start_height → protocol_version
//   - end_height → start_height
//   - request_id → end_height (fails, tries to parse string as u64)
```

### Scenario 2: Binaries Are Mismatched Versions

Possible that:
- Server Beta is running v0.9.52-beta or earlier (has `#[serde(default)]`)
- Server Alpha is running v0.9.53-beta or later (no `#[serde(default)]`)
