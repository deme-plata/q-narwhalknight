## Implementation Details

### Changes Made

**File**: `crates/q-storage/src/lib.rs`

#### 1. Enhanced QStorage Struct (Lines 75-93)

**Before**:
```rust
pub struct QStorage {
    hot_db: Arc<dyn KVStore>,
    cold_db: Arc<dyn KVStore>,
    // ... other fields
}
```

**After**:
```rust
pub struct QStorage {
    /// Hot database (RocksDB) - blocks, vertices, certificates
    hot_db: Arc<dyn KVStore>,
    /// Concrete RocksDBKV reference for advanced operations like pruning
    hot_db_concrete: Arc<RocksDBKV>,  // ← NEW FIELD
    /// Cold database (RocksDB) - large Narwhal payloads
    cold_db: Arc<dyn KVStore>,
    // ... other fields
}
```

#### 2. Updated Constructor (Lines 115-160)

**Key Change**: Store both trait object and concrete type references

```rust
// Configure hot database (frequent access)
let hot_path = data_dir.join("hot");
let hot_db_concrete = Arc::new(
    RocksDBKV::open_hot_db(&hot_path)
        .await
        .context("Failed to open hot database")?,
);

// Configure cold database (large payloads)
let cold_path = data_dir.join("cold");
let cold_db = Arc::new(
    RocksDBKV::open_cold_db(&cold_path)
        .await
        .context("Failed to open cold database")?,
);

// Create trait object reference from concrete type
let hot_db: Arc<dyn KVStore> = hot_db_concrete.clone();

// ... manifest, sync_protocol, snapshot_manager, metrics initialization

let storage = Self {
    hot_db,
    hot_db_concrete,  // ← NEW FIELD INITIALIZED
    cold_db,
    manifest,
    sync_protocol,
    snapshot_manager,
    metrics,
    node_id,
    data_dir,
};
```

**Architecture Rationale**:
- Maintains existing `Arc<dyn KVStore>` for trait-based polymorphism
- Adds separate `Arc<RocksDBKV>` for concrete type access
- Both references point to the same underlying RocksDB instance
- Zero overhead (Arc is just reference counting)
- No unsafe code or downcasting required

#### 3. Accessor Method (Lines 1939-1943)

```rust
/// Get access to hot RocksDB for advanced operations like pruning
/// This returns the concrete RocksDBKV type which supports pruning operations
pub fn get_hot_db(&self) -> Arc<RocksDBKV> {
    self.hot_db_concrete.clone()
}
```

**Method Characteristics**:
- **Public API**: Accessible from `q-api-server` and other modules
- **Returns**: `Arc<RocksDBKV>` with full access to pruning methods
- **Thread-safe**: Arc provides safe concurrent access
- **Cheap**: Arc::clone only increments reference count
- **Type-safe**: No runtime downcasting or Result wrapping

## Usage from API Server

### Phase 2 Integration Pattern

From `crates/q-api-server/src/main.rs`:

```rust
// Background pruning scheduler
{
    let app_state_pruning = app_state.clone();

    tokio::spawn(async move {
        info!("✂️  Starting adaptive pruning scheduler (every 1 hour)...");
        let mut interval = tokio::time::interval(tokio::time::Duration::from_secs(3600));

        loop {
            interval.tick().await;

            // Get current blockchain height
            let current_height = app_state_pruning.node_status.read().await.current_height;

            // Only prune if we have sufficient blockchain data
            if current_height > 100_000 {
                info!("✂️  Running adaptive pruning at height {}", current_height);

                // ✅ Access RocksDB via get_hot_db()
                let hot_db = app_state_pruning.storage_engine.get_hot_db();

                match hot_db.prune_old_blocks(current_height).await {
                    Ok(stats) => {
                        info!("✅ Pruning complete: {} blocks pruned, {} blocks retained",
                              stats.pruned_blocks, stats.retained_blocks);
                        info!("💾 Storage saved: {:.2} MB ({:.1}% reduction)",
                              stats.space_saved as f64 / 1_000_000.0,
                              (stats.space_saved as f64 / stats.storage_before as f64) * 100.0);
                    }
                    Err(e) => {
                        warn!("⚠️  Pruning failed: {}", e);
                    }
                }
            } else {
                debug!("⏳ Skipping pruning (current height: {} < 100K minimum)", current_height);
            }
        }
    });

    info!("✅ Adaptive pruning scheduler started");
}
```

## Architecture Benefits

### 1. Clean Separation of Concerns

**Trait-based Interface** (`Arc<dyn KVStore>`):
- Generic storage operations (get, put, delete, scan)
- Used by: manifest, sync_protocol, snapshot_manager
- Enables future storage backend alternatives (e.g., TiKV, FoundationDB)

**Concrete Type Access** (`Arc<RocksDBKV>`):
- RocksDB-specific operations (pruning, compaction, column families)
- Used by: pruning scheduler, advanced admin operations
- Direct access to `prune_old_blocks()`, `get_blockchain_height()`, etc.

### 2. Zero Runtime Overhead

- **No Downcasting**: Avoids `Any` trait and runtime type checks
- **No Option Wrapping**: Returns concrete type directly
- **Same Memory**: Both Arc references point to same RocksDB instance
- **Cheap Cloning**: Arc::clone is just atomic reference count increment

### 3. Type Safety

```rust
// Compile-time guaranteed access to pruning methods
let hot_db: Arc<RocksDBKV> = storage_engine.get_hot_db();
let stats = hot_db.prune_old_blocks(height).await?;  // ✅ Type-checked at compile time
```

vs unsafe downcasting:

```rust
// ❌ Runtime overhead + unsafe code
let hot_db_any: &dyn Any = &storage_engine.hot_db;
if let Some(rocks_db) = hot_db_any.downcast_ref::<RocksDBKV>() {
    // May fail at runtime
}
```

### 4. Backward Compatibility

**Existing Code Unaffected**:
- All current storage operations continue to use `hot_db: Arc<dyn KVStore>`
- No changes required to `manifest`, `sync_protocol`, `snapshot_manager`
- Only new pruning scheduler uses `get_hot_db()`

## Performance Impact

### Memory Overhead

**Additional Memory**: ~16 bytes per `QStorage` instance
- 1 additional `Arc<RocksDBKV>` pointer (8 bytes)
- Arc internal ref count (8 bytes)

**Total Impact**: Negligible (<0.001% of typical node memory)

### Runtime Overhead

**get_hot_db() Cost**:
- Arc::clone: 1 atomic increment (~1-2 CPU cycles)
- No heap allocations
- No locks or synchronization

**Comparison**:
- Direct field access: 0 cycles
- get_hot_db(): ~1-2 cycles
- Downcasting: ~100-1000 cycles (type checks, vtable lookups)

**Verdict**: ✅ Essentially free
