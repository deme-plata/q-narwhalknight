### **Flaw #3: Race Condition in Rate Limiter** 🔴 CRITICAL
**Location**: `crates/q-storage/src/zk_block_request_auth.rs:99-127`

**Issue**:
```rust
pub async fn check_rate_limit(&self, peer_id: &PeerId) -> Result<bool> {
    let mut rate_limiter = self.rate_limiter.write().await;  // Lock acquired

    let now = Instant::now();
    let entry = rate_limiter.entry(*peer_id).or_insert((0, now));

    // Reset counter if 1 minute has passed
    if now.duration_since(entry.1).as_secs() >= 60 {
        entry.0 = 0;
        entry.1 = now;
    }

    // Check if rate limit exceeded
    if entry.0 >= self.max_requests_per_minute {
        warn!("⚠️ [ZK BLOCK AUTH] Rate limit exceeded");
        return Ok(false);  // ← Lock released here
    }

    // Increment request count
    entry.0 += 1;  // ← But we still increment!
    Ok(true)
}
```

**Root Cause**:
When rate limit is exceeded, we return `Ok(false)` but the write lock is held for the entire function. This is correct. However, there's a **logical bug**:

```rust
// Caller code in verify_block_request():
if !self.check_rate_limit(peer_id).await? {
    warn!("🚫 [ZK BLOCK AUTH] Rate limit exceeded");
    self.record_rate_limit_violation(peer_id).await;  // ← Calls ANOTHER write lock!
    return Ok(false);
}
```

The caller tries to acquire ANOTHER write lock on `peer_reputation` which can deadlock if:
1. Thread A holds `rate_limiter` lock
2. Thread B holds `peer_reputation` lock
3. Thread A tries to get `peer_reputation` lock (deadlock!)
4. Thread B tries to get `rate_limiter` lock (deadlock!)

**Impact**:
- ❌ **Potential deadlock** under high request load
- ❌ **Node hangs** when processing block requests
- ❌ **DoS vector** - Attacker sends many requests to trigger deadlock

**Fix Required**:
```rust
pub async fn check_rate_limit(&self, peer_id: &PeerId) -> Result<RateLimitResult> {
    let mut rate_limiter = self.rate_limiter.write().await;
    let now = Instant::now();
    let entry = rate_limiter.entry(*peer_id).or_insert((0, now));

    if now.duration_since(entry.1).as_secs() >= 60 {
        entry.0 = 0;
        entry.1 = now;
    }

    if entry.0 >= self.max_requests_per_minute {
        return Ok(RateLimitResult::Exceeded);
    }

    entry.0 += 1;
    Ok(RateLimitResult::Allowed)
}

// Caller:
match self.check_rate_limit(peer_id).await? {
    RateLimitResult::Exceeded => {
        // Don't call record_rate_limit_violation (separate lock!)
        warn!("Rate limit exceeded");
        return Ok(false);
    }
    RateLimitResult::Allowed => { /* continue */ }
}
```

### **Bug #4: Memory Leak in Reputation Tracking** 🟠 HIGH
**Location**: `crates/q-network/src/zk_peer_height_proof.rs:162-177`

**Issue**:
```rust
/// Reputation: peer_id -> (successful_proofs, failed_proofs)
peer_reputation: Arc<RwLock<std::collections::HashMap<PeerId, (u64, u64)>>>,

async fn record_proof_success(&self, peer_id: &PeerId) {
    let mut reputation = self.peer_reputation.write().await;
    let entry = reputation.entry(*peer_id).or_insert((0, 0));
    entry.0 += 1; // Increment successful proofs
    // ← No cleanup! HashMap grows FOREVER
}
```

**Root Cause**:
The `peer_reputation` HashMap **NEVER removes entries**. Over time:
- Day 1: 100 peers = 100 HashMap entries
- Day 30: 50,000 unique peers = 50,000 HashMap entries
- Day 365: 1.8 million peers = **18 MB memory leak**

**Impact**:
- ❌ **Unbounded memory growth** over time
- ❌ **Node crashes** after months of operation
- ❌ **Performance degradation** as HashMap grows

**Fix Required**:
```rust
// Add periodic cleanup task
pub async fn cleanup_old_reputations(&self) {
    const MAX_REPUTATION_AGE: Duration = Duration::from_secs(7 * 24 * 3600); // 1 week

    let mut reputation = self.peer_reputation.write().await;
    let mut last_seen: HashMap<PeerId, Instant> = HashMap::new();

    // Track last interaction
    // Remove entries not seen in > 1 week
    reputation.retain(|peer_id, _| {
        last_seen.get(peer_id)
            .map(|time| time.elapsed() < MAX_REPUTATION_AGE)
            .unwrap_or(false)
    });
}

// Add to periodic task:
tokio::spawn(async move {
    let mut interval = tokio::time::interval(Duration::from_secs(3600)); // Hourly
    loop {
        interval.tick().await;
        height_verifier.cleanup_old_reputations().await;
    }
});
```

### **Bug #5: Banned Peers Can Reconnect** 🟠 HIGH
**Location**: `crates/q-network/src/zk_peer_height_proof.rs:46-58`

**Issue**:
```rust
pub struct PeerHeightVerifier {
    banned_peers: Arc<RwLock<std::collections::HashSet<PeerId>>>,
    // ...
}

pub async fn is_banned(&self, peer_id: &PeerId) -> bool {
    self.banned_peers.read().await.contains(peer_id)
}
```

**Root Cause**:
The ban list is **in-memory only**. When the node restarts:
1. Banned peer list is cleared
2. Malicious peers reconnect
3. They get 3 more attempts before ban
4. **Repeat attack** every time node restarts

**Impact**:
- ❌ **Bans don't persist** across restarts
- ❌ **Malicious peers can retry attacks** indefinitely
- ❌ **No long-term protection** from repeat offenders

**Fix Required**:
```rust
// Persist bans to RocksDB
const CF_BANNED_PEERS: &str = "banned_peers";

pub async fn ban_peer(&self, peer_id: &PeerId) {
    let mut banned = self.banned_peers.write().await;
    banned.insert(*peer_id);

    // Persist to database
    if let Some(db) = &self.banned_peers_db {
        let key = peer_id.to_bytes();
        let value = bincode::serialize(&BanRecord {
            peer_id: *peer_id,
            ban_timestamp: SystemTime::now(),
            reason: "Invalid ZK proofs".to_string(),
        }).unwrap();

        db.put(CF_BANNED_PEERS, &key, &value).await.ok();
    }

    error!("🚨 PEER BANNED: {} (persisted to DB)", peer_id);
}

// Load bans on startup
pub async fn load_banned_peers(&self) -> Result<()> {
    if let Some(db) = &self.banned_peers_db {
        let mut banned = self.banned_peers.write().await;

        for (key, value) in db.iterate(CF_BANNED_PEERS).await? {
            let ban_record: BanRecord = bincode::deserialize(&value)?;
            banned.insert(ban_record.peer_id);
        }

        info!("Loaded {} banned peers from database", banned.len());
    }
    Ok(())
}
```

### **Issue #8: Inefficient Rate Limiter** 🟢 LOW
**Location**: `crates/q-storage/src/zk_block_request_auth.rs:99-127`

**Issue**:
The current rate limiter uses a **write lock** even for read-only operations:

```rust
pub async fn check_rate_limit(&self, peer_id: &PeerId) -> Result<bool> {
    let mut rate_limiter = self.rate_limiter.write().await;  // ← Always write lock!
    // ...
}
```

**Root Cause**:
Every rate limit check requires exclusive write access, even if just reading current count. This serializes ALL requests.

**Impact**:
- 📉 **Poor concurrency** under high load
- 📉 **Unnecessary lock contention**
- 📉 **Reduced throughput** (only one request at a time)

**Fix**: Use a more efficient token bucket or sliding window rate limiter with atomic operations.
