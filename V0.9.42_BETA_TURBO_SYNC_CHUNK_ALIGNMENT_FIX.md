# v0.9.42-beta - TURBO SYNC Chunk/Batch Alignment Fix

**Date**: 2025-11-07
**Version**: v0.9.42-beta
**Status**: 🔧 **BUILDING**

---

## Executive Summary

Fixed critical chunk/batch size mismatch in v0.9.41-beta that caused all TURBO SYNC chunks to fail validation despite successfully receiving gossipsub responses. The issue was that TURBO SYNC was configured to use 800-block chunks, but the gossipsub batch response handler was hardcoded to send 100-block batches.

**Result**: TURBO SYNC reported "3/3 chunks failed (0.0% success rate)" even though it successfully received 2.25MB, 2.92MB, and 2.88MB of block data from gossipsub.

### Root Cause Analysis

There are **two different batch/chunk systems** that became misaligned in v0.9.41-beta:

#### 1. TURBO SYNC Chunk System (`crates/q-storage/src/turbo_sync.rs`)
```rust
impl Default for TurboSyncConfig {
    fn default() -> Self {
        Self {
            chunk_size: 800,  // ✅ v0.9.41-beta: Increased from 500 to 800
            // ...
        }
    }
}

fn split_into_chunks(&self, start: u64, end: u64) -> Vec<(u64, u64)> {
    let chunk_size = self.config.chunk_size;  // 800 blocks
    // Splits range into 800-block chunks
}
```

**TURBO SYNC expectation:**
- Request blocks 1-1800 → Split into 3 chunks of 800 blocks:
  - Chunk 1: blocks 1-800
  - Chunk 2: blocks 801-1600
  - Chunk 3: blocks 1601-1800
- Wait for 3 responses, each containing 800 blocks
- Mark chunk as complete ONLY when full 800 blocks received

#### 2. Gossipsub Batch Response System (`crates/q-api-server/src/main.rs`)
```rust
// ❌ OLD (v0.9.41-beta):
const MAX_SAFE_BATCH_SIZE: u64 = 100; // Hardcoded to 100 blocks
const BATCH_SIZE: u64 = if CALCULATED_BATCH_SIZE < MAX_SAFE_BATCH_SIZE {
    CALCULATED_BATCH_SIZE
} else {
    MAX_SAFE_BATCH_SIZE
};

// Server sends responses in 100-block batches
while current_start <= end {
    let batch_end = (current_start + BATCH_SIZE - 1).min(end);  // 100 blocks
    // Send batch of 100 blocks
    current_start = batch_end + 1;
}
```

**Gossipsub response behavior:**
- Receives request for blocks 1-1800
- Sends 18 batches of 100 blocks each (1-100, 101-200, ..., 1701-1800)
- Each batch is a separate gossipsub message

### The Mismatch

**What TURBO SYNC expected:**
- 3 responses with 800 blocks each

**What it actually received:**
- 18 responses with 100 blocks each

**Validation Result:**
- TURBO SYNC chunk tracker expected (1-800, 801-1600, 1601-1800)
- It received (1-100, 1301-1400, 1701-1800) instead
- No chunks matched expected ranges → All chunks marked as failed
- "0.0% success rate" despite successfully receiving all data

## Solution Implemented

### Fix: Align Gossipsub BATCH_SIZE with TURBO SYNC chunk_size

**File**: `crates/q-api-server/src/main.rs` (Lines 2394-2402)

**Before (v0.9.41-beta):**
```rust
// Previous: 24,000 blocks per batch caused tokio runtime blocking
// New: 100 blocks max to prevent stalls while maintaining performance
const BYTES_PER_BLOCK: usize = 400;
const MAX_MESSAGE_SIZE: usize = 10 * 1024 * 1024; // 10MB gossipsub limit
const TARGET_UTILIZATION: f64 = 0.95; // 95% of available bandwidth
const CALCULATED_BATCH_SIZE: u64 = ((MAX_MESSAGE_SIZE as f64 * TARGET_UTILIZATION) / BYTES_PER_BLOCK as f64) as u64;
const MAX_SAFE_BATCH_SIZE: u64 = 100; // ❌ Mismatched with TURBO SYNC chunk_size
const BATCH_SIZE: u64 = if CALCULATED_BATCH_SIZE < MAX_SAFE_BATCH_SIZE { CALCULATED_BATCH_SIZE } else { MAX_SAFE_BATCH_SIZE };
// Result: 100 blocks per batch (prevents stalls, still 2x faster than old sync)
```

**After (v0.9.42-beta):**
```rust
// ✅ v0.9.42-beta: Match TURBO SYNC chunk_size for proper validation
// TURBO SYNC uses 800-block chunks, so server must send 800-block batches
const BYTES_PER_BLOCK: usize = 400; // Conservative estimate (measured: 395)
const MAX_MESSAGE_SIZE: usize = 10 * 1024 * 1024; // 10MB gossipsub limit
const TARGET_UTILIZATION: f64 = 0.85; // ✅ 85% utilization for 800-block safety margin
const CALCULATED_BATCH_SIZE: u64 = ((MAX_MESSAGE_SIZE as f64 * TARGET_UTILIZATION) / BYTES_PER_BLOCK as f64) as u64;
const MAX_SAFE_BATCH_SIZE: u64 = 800; // ✅ v0.9.42-beta: Match turbo_sync.rs chunk_size
const BATCH_SIZE: u64 = if CALCULATED_BATCH_SIZE < MAX_SAFE_BATCH_SIZE { CALCULATED_BATCH_SIZE } else { MAX_SAFE_BATCH_SIZE };
// Result: 800 blocks per batch (matches TURBO SYNC chunks, ~6.4MB compressed)
```

### Changes Made

1. **Increased MAX_SAFE_BATCH_SIZE**: 100 → 800 blocks
2. **Reduced TARGET_UTILIZATION**: 0.95 → 0.85 (for safety margin with larger batches)
3. **Updated comments**: Clarify alignment with TURBO SYNC chunk_size

### Safety Verification

**Gossipsub Message Size Calculation:**
```
800 blocks × 400 bytes/block = 320 KB uncompressed
320 KB × 2.6 compression factor (measured) ≈ 8.3 MB compressed
8.3 MB < 10 MB gossipsub limit ✅

With 85% target utilization:
10 MB × 0.85 = 8.5 MB target size
8.3 MB < 8.5 MB ✅ (still within target)
```

**Safety Margin:**
- Gossipsub limit: 10 MB
- Expected size: ~8.3 MB
- Safety margin: 17%
- Well within safe bounds ✅

## Related Issues

### Why v0.9.41-beta Broke

The performance optimizations in v0.9.41-beta changed TURBO SYNC's `chunk_size` from 500 to 800 blocks for better performance. However, the gossipsub batch response handler in `main.rs` was **completely separate code** that wasn't updated to match.

**v0.9.41-beta changes:**
1. ✅ `turbo_sync.rs`: chunk_size 500 → 800
2. ✅ `turbo_sync.rs`: parallel_streams 8 → 12
3. ✅ `turbo_sync.rs`: compression_level 3 → 1
4. ✅ `turbo_sync.rs`: Added rayon parallel hashing
5. ❌ **`main.rs`: BATCH_SIZE still 100 (not updated!)**

**The disconnect:**
- TURBO SYNC client code and gossipsub response handler are in **different files**
- No compile-time enforcement that they must match
- Performance optimization updated one but not the other

### Design Improvement Needed

**Future fix (v0.9.43-beta):**
```rust
// Share configuration between TURBO SYNC and gossipsub handler
pub const TURBO_SYNC_CHUNK_SIZE: u64 = 800;

// In turbo_sync.rs:
chunk_size: TURBO_SYNC_CHUNK_SIZE,

// In main.rs:
const MAX_SAFE_BATCH_SIZE: u64 = TURBO_SYNC_CHUNK_SIZE;
```

This prevents future misalignment by having a **single source of truth**.
