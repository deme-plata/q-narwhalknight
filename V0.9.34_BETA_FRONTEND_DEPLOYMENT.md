## 🎯 Fixes Included in v0.9.34-beta

### Critical Bug Fix: Balance Fluctuation (670 → 68 QUG)

**Problem**: User reported "sometimes ive correct balanc 670 sometimes ive only 68"

**Root Cause**: **Decimal place inconsistency** between backend and frontend:
- Backend: Uses **9 decimals** (1,000,000,000 base units = 1 QUG) ✅
- Frontend: Used **8 decimals** (100,000,000 base units = 1 QUG) ❌

**Impact**: Balance displayed 10x too high in some UI components (670 instead of 69)

**Solution**: Updated frontend to match backend's 9-decimal standard

## 🔢 The Math Behind the Bug

**Actual Balance**: `69,414,022,000` base units

### With 8 Decimals (WRONG):
```
69,414,022,000 / 100,000,000 = 694.14 QUG ≈ 670 QUG (10x too high!)
```

### With 9 Decimals (CORRECT):
```
69,414,022,000 / 1,000,000,000 = 69.414 QUG ≈ 68 QUG (correct)
```

**Why User Saw Both**:
- Dashboard transaction history: Used 8 decimals → **670 QUG** ❌
- Faucet response: Used backend value → **68 QUG** ✅
- Result: Balance appeared to fluctuate unpredictably

## 💡 Why This Bug Occurred

**Historical Context**:

1. **Bitcoin Legacy**: QUG initially copied Bitcoin's 8-decimal convention (satoshis)
2. **Backend Evolution**: Backend changed to 9 decimals for better precision
3. **Frontend Left Behind**: Frontend constants never updated to match
4. **Result**: 10x display error (69 displayed as 694)

**Why Some Components Showed Correct Value**:
- Faucet endpoint: Returns `balance_qnk` field from backend (9 decimals) ✅
- Dashboard: Converted from base units using 8 decimals ❌
- API responses: Backend always correct (9 decimals) ✅
