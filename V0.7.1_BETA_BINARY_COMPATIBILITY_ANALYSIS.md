# v0.7.1-beta: Binary Compatibility Issue - Complete Analysis

**Date:** November 2, 2025, 09:00 CET
**Issue:** Invalid block pack requests with reversed start/end heights
**Status:** ROOT CAUSE IDENTIFIED - Fix ready for implementation

---

## 🚨 Problem Summary

**Server Alpha Docker (v0.7.1-beta) Cannot Sync** due to receiving malformed block pack requests from Server Beta.

**Error Pattern (from `looksgoodbutslow6.ini`):**
```
2025-11-02T07:28:14.272327Z ERROR q_api_server: 🚫 [TURBO SYNC P2P] INVALID REQUEST: end_height (49) < start_height (52). Request is malformed or corrupted.
2025-11-02T07:28:14.272355Z ERROR q_api_server: 🚫 [TURBO SYNC P2P] Request details: start=52, end=49, id=D3KooWFgEekf72dDYvP5NvZgPQcdsvRG1M5z6BH3gs1KWZ8meS
2025-11-02T07:28:14.272365Z ERROR q_api_server: 🚫 [TURBO SYNC P2P] Peer may be running incompatible binary version - REJECTING
```

**Impact:**
- Server Alpha Docker stuck at height 4 out of 4,736 (99.9% behind)
- ALL block pack requests rejected every 30 seconds
- Turbo sync P2P completely blocked
- Only way to sync: Slow HTTP fallback (~20 blocks/sec vs 1,000 blocks/sec)

## 🔍 Root Cause Analysis

### Affected Nodes

**Server Alpha Docker (RECEIVER - Rejecting requests):**
- Container: `q-v0.7.1-beta`
- Version: v0.7.1-beta
- Peer ID: `12D3KooWRjv8efHi6Hk9rHxfDsTynbBvqRLsiExbdWgnWmRvCNKU`
- Current Height: 4
- Network Height: 4,736
- Status: ❌ Sync blocked by invalid requests

**Server Beta (SENDER - Creating bad requests):**
- Host: 185.182.185.227:9001
- Version: v0.7.1-beta
- Peer ID: `12D3KooWFgEekf72dDYvP5NvZgPQcdsvRG1M5z6BH3gs1KWZ8meS`
- Current Height: 27,948+ (mining successfully)
- Status: ✅ Running fine BUT sending malformed requests

### The Malformed Requests

**What Server Beta is sending:**
```rust
BlockPackRequest {
    start_height: 52,    // ❌ HIGHER number
    end_height: 49,      // ❌ LOWER number (INVALID!)
    requester_id: "12D3KooWFgEekf72dDYvP5NvZgPQcdsvRG1M5z6BH3gs1KWZ8meS"
}
```

**What Server Beta SHOULD be sending:**
```rust
BlockPackRequest {
    start_height: 5,     // ✅ Lower bound
    end_height: 4333,    // ✅ Higher bound (end > start)
    requester_id: "..."
}
```

### Why Is This Happening?

**Hypothesis 1: Old Height Recovery Bug (MOST LIKELY)**

Server Beta's database MAY have had a corrupted height pointer at some point in the past:
1. Server Beta was at height 52 (actual blockchain)
2. Height pointer got corrupted/reset to 49
3. Server Beta created a request: "Give me blocks from my current height (52) to the network height (49)"
4. Result: Backwards request (start=52, end=49)

**Evidence:**
- Server Beta is NOW at height 27,948+ (recovered successfully)
- But old malformed requests are STILL being broadcast via gossipsub
- This matches the "height reset bug" we saw in previous versions

**Hypothesis 2: Serialization Bug (LESS LIKELY)**

Postcard serialization may be reversing the field order:
```rust
// Sent as:
BlockPackRequest { start: 49, end: 52 }

// Received as (fields swapped):
BlockPackRequest { start: 52, end: 49 }
```

**Evidence AGAINST this:**
- Server Alpha's OWN requests work fine (3-4025, 4-4164, 5-4333)
- Only Server Beta's requests are malformed
- Same v0.7.1-beta binary on both nodes

### Why Does Server Beta Keep Sending Bad Requests?

**Persistent Gossipsub Messages:**

Gossipsub has message caching and relay behavior:
1. Server Beta published a bad request when it had corrupted height
2. Message was cached in gossipsub's message cache (default: 5 minute TTL)
3. Server Beta recovered its height BUT old message still cached
4. Gossipsub re-broadcasts cached messages to new peers
5. Server Alpha Docker (fresh start) receives OLD cached bad request

**Alternative:** Periodic re-publishing of stale requests from corrupted state

## ✅ Solution: Add Backwards-Compatible Request Validation

### Fix: Auto-Swap Reversed Heights

**File:** `crates/q-api-server/src/main.rs` (block pack request handler)

**Location:** Around line 2900 (where block pack requests are processed)

**Code Change:**
```rust
// 🔄 v0.7.2-beta: Auto-fix reversed heights for backwards compatibility
// This handles the case where older/buggy peers send requests with start > end
// due to height pointer corruption or serialization bugs

if request.end_height < request.start_height {
    warn!(
        "🔄 [TURBO SYNC P2P] Auto-fixing reversed heights from peer {}: {} <-> {}",
        requester_id, request.start_height, request.end_height
    );

    // Swap them to fix the request
    let temp = request.start_height;
    request.start_height = request.end_height;
    request.end_height = temp;

    info!(
        "✅ [TURBO SYNC P2P] Request corrected: now requesting blocks {}-{}",
        request.start_height, request.end_height
    );
}

// Now validate AFTER auto-fix
if request.end_height < request.start_height {
    error!(
        "🚫 [TURBO SYNC P2P] INVALID REQUEST even after auto-fix: end_height ({}) < start_height ({}). Request is critically malformed.",
        request.end_height, request.start_height
    );
    error!("🚫 [TURBO SYNC P2P] Request details: start={}, end={}, id={}",
           request.start_height, request.end_height, requester_id);
    error!("🚫 [TURBO SYNC P2P] This should never happen - rejecting");
    return; // Still invalid even after swap - reject
}

// Continue with normal processing...
info!("🚀 [TURBO SYNC P2P] Processing request for blocks {}-{} from peer {}",
      request.start_height, request.end_height, requester_id);
```

### Benefits of This Approach

✅ **Backwards Compatible** - Handles buggy requests from older nodes
✅ **Graceful Degradation** - Fixes instead of rejecting
✅ **Clear Logging** - Warns about reversed heights so we can track frequency
✅ **Safety Check** - Still rejects if swap doesn't fix it
✅ **No Breaking Changes** - Works with all existing protocol versions

### Alternative Solution: Strict Version Enforcement (Not Recommended)

```rust
// ❌ This approach breaks network connectivity for users on older versions
if peer_protocol_version < "0.7.2" {
    warn!("🚫 Rejecting connection from outdated peer: {} (version {})",
          peer_id, peer_protocol_version);
    swarm.disconnect_peer_id(peer_id).ok();
    return;
}
```

**Why Not Recommended:**
- Forces ALL users to upgrade immediately
- Breaks sync for nodes that haven't updated yet
- Creates network fragmentation
- User-hostile (no migration path)

## 🔧 Technical Notes

### Why the Auto-Swap Is Safe

1. **Preserves Intent:** If a peer requests blocks 52-49 (backwards), they clearly meant 49-52 (forwards)
2. **Idempotent:** Swapping twice returns to original (but validation rejects original)
3. **Logged:** Every swap is logged with WARN level for auditing
4. **Fallback:** If swap doesn't fix it, still reject (safety net)
5. **No Side Effects:** Only affects the local request processing, doesn't modify database

### Gossipsub Message Caching Behavior

**Default TTL:** 5 minutes (libp2p gossipsub default)
**Cache Size:** ~100 messages per topic (configurable)
**Relay Behavior:** Cached messages re-broadcast to newly connected peers

**Why This Causes the Issue:**
1. Server Beta published bad request at 07:23:14 (when height was corrupted)
2. Message cached in gossipsub for 5 minutes
3. Server Alpha Docker connected at 07:26:22
4. Gossipsub relayed cached bad request to new peer (Server Alpha)
5. Request is 3 minutes old but still delivered
6. Server Beta has already recovered (height 27,948+) but old message persists

### Alternative: Flush Gossipsub Cache (Not Recommended)

```rust
// This would require modifying libp2p internals
swarm.behaviour_mut().gossipsub.flush_message_cache();
```

**Why Not:**
- Requires patching libp2p (maintenance burden)
- Loses legitimate cached messages
- Doesn't prevent future occurrences
- Auto-swap is simpler and more robust
