## ✅ Fix 1: Challenge Expiry Grace Period (COMPLETED)

### **Problem Identified**:
v1.0.4-beta implementation had a subtle but critical bug:
- Cache expired after exactly 120 seconds
- Triggered regeneration even at same height
- Changed challenge hash during temporary stalls
- Caused miner confusion after 2 minutes of no solutions

### **Root Cause**:
```rust
// v1.0.4-beta BUG:
if challenge.block_height == block_height && challenge.expires_at > chrono::Utc::now() {
    return cached;  // Only if not expired
}
// Problem: expires_at check causes regeneration at 120s mark
```

### **Solution Implemented**:
**File**: `crates/q-api-server/src/handlers.rs` (lines 4407-4451)

**Three-tier expiry logic**:
1. **Fresh (0-120s)**: Normal cache hit, return immediately
2. **Grace period (120-150s)**: Warn but still return cached (prevents hash change)
3. **Stale (>150s)**: Force regeneration

**Code**:
```rust
if challenge.block_height == block_height {
    let age_seconds = (chrono::Utc::now() - challenge.issued_at).num_seconds();

    if age_seconds < 120 {
        // Normal cache hit - challenge is fresh
        return cached_response;
    } else if age_seconds < 150 {
        // Grace period: Warn but still return cached
        warn!("Challenge age {}s (expired {}s ago), returning cached anyway (grace period)",
              age_seconds, age_seconds - 120);
        return cached_response;
    } else {
        // Challenge too old (>150s) - force regeneration
        warn!("Challenge {} seconds old - forcing regeneration", age_seconds);
        drop(cached);  // Fall through to regeneration
    }
}
```

### **Benefits**:
- ✅ Prevents premature hash regeneration during brief stalls
- ✅ 30-second grace window provides stability during network delays
- ✅ Clear warning logs help identify actual stalls without causing them
- ✅ Smoother degradation during network issues

### **Testing Plan**:
1. Deploy v1.0.5-beta and observe challenge behavior
2. Monitor logs for grace period warnings
3. Verify challenge hash remains stable during 2-3 minute stalls
4. Confirm regeneration occurs after 150 seconds if height doesn't advance

**Status**: ✅ **IMPLEMENTED** - Code complete, compilation check in progress

## ⏳ Fix 2: Consensus-Bound Challenge Generation (PENDING)

### **Problem**:
Current challenges use timestamp-based generation:
```rust
let challenge_data = format!("block_{}_time_{}", block_height, issued_at.timestamp());
```

This is **non-deterministic** - different nodes generate different challenges at same height.

### **Solution Design**:
Bind challenges to consensus-stable inputs:

```rust
struct ChallengeInput {
    version: &'static [u8],     // b"QNK/1"
    parent_hash: [u8; 32],      // Previous block hash
    height: u64,
    difficulty: [u8; 32],
    vdf_iters: u32,
    lane_id: u8,                // 0-7 for 8-lane producers
}

fn make_challenge(input: &ChallengeInput) -> [u8; 32] {
    let mut h = blake3::Hasher::new();
    h.update(input.version);
    h.update(&input.parent_hash);
    h.update(&input.height.to_le_bytes());
    h.update(&input.difficulty);
    h.update(&input.vdf_iters.to_le_bytes());
    h.update(&[input.lane_id]);
    *h.finalize().as_bytes()
}
```

### **Implementation Steps**:
1. Modify `get_mining_challenge()` to accept optional lane_id parameter
2. Fetch parent block hash from storage
3. Generate deterministic challenge based on consensus inputs
4. Update cache key to include lane_id
5. Test with multiple nodes - verify identical challenges

## ⏳ Fix 3: Solution Deduplication (PENDING)

### **Problem**:
No protection against duplicate solution submissions:
- Miners can spam same solution multiple times
- Wastes network bandwidth and processing
- No tracking of recent submissions

### **Solution Design**:
Ring buffer tracking `(height, lane_id, solution_hash)`:

```rust
pub struct SolutionDedupCache {
    cache: Arc<RwLock<HashMap<(u64, u8, [u8; 32]), chrono::DateTime<Utc>>>>,
}

impl SolutionDedupCache {
    pub fn insert(&self, height: u64, lane_id: u8, hash: [u8; 32]) -> bool {
        let mut cache = self.cache.write();
        let now = chrono::Utc::now();

        // Clean expired entries (>5 minutes old)
        cache.retain(|_, timestamp| {
            now.signed_duration_since(*timestamp).num_seconds() < 300
        });

        // Check if already exists
        if cache.contains_key(&(height, lane_id, hash)) {
            return false; // Duplicate
        }

        cache.insert((height, lane_id, hash), now);
        true // New solution
    }
}
```

### **Integration Points**:
1. Add `solution_dedup: SolutionDedupCache` to `AppState`
2. Check before accepting solutions in `submit_mining_solution()`
3. Return error for duplicates: `"Solution already submitted"`
4. Log duplicate attempts for monitoring
